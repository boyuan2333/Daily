# Agent Collaboration Playbook

本文件定义人、Daily 仓库和不同工作区 Agent 之间的协作方式。它解决的是上下文连续性和任务交接问题，不是 Daily 应用内部的 AI 功能规格。

## 1. 先分清两种 AI

### 外部 Agent（现在就使用）

外部 Agent 负责读取仓库、澄清需求、写计划、实现代码、运行测试和审查变更。它可以在同一工作区的不同对话、不同 Git worktree、不同电脑上工作。

### Daily 内部 AI（后续再做）

内部 AI 只作为用户主动触发的 Planning 辅助。它可以把模糊目标整理成路线草稿，但不能自动激活路线，不能在 Guide 模式重新规划，也不能替代本地状态机和持久化。

因此，当前下一步不是先把 AI 接进程序，而是先固定 Agent 协作协议，再把已确认的产品行为拆成实现计划。

## 2. 所有 Agent 的共同前置提示词

把下面内容放在每个新对话的第一条消息中，然后再追加具体任务：

```text
你正在参与 Daily 仓库的工作。先不要修改文件。

请依次读取：
1. AGENTS.md
2. docs/PRODUCT_SPEC.md
3. docs/ACCEPTANCE.md
4. docs/IMPLEMENTATION_PLAN.md
5. docs/DAILY_UI_UPDATE_NOTES.md（如果任务涉及体验或 UI）
6. docs/UI_FIX_BACKLOG.md（如果任务涉及 UI 修复）

然后检查：
- 当前工作区路径
- git status --short --branch
- git log -5 --oneline
- 与本任务相关的现有代码、测试和未提交修改

先用简短文字报告：
- 你理解的任务
- 受影响的验收标准（AC 编号）
- 准备读取或修改的文件
- 现有未提交修改是否可能冲突
- 验证方式

遵守以下边界：
- 不猜测未确认的产品决定；把它标为 open question。
- 不重置、回滚、覆盖或清理不是你创建的修改。
- 不在 Guide 模式增加路线选择、建议列表或状态解释要求。
- 不把用户捕捉内容改写成任务，也不改变 activeRouteId。
- 未获得明确范围前不顺手重构或修改无关文件。
- 在确认范围后才编辑；编辑后必须运行与改动匹配的测试或构建验证。
```

## 3. 同一工作区、不同对话

这种情况共享同一个 working tree，风险最高。使用下面的附加提示词：

```text
这是同一工作区的续接对话。工作区可能有用户或其他 Agent 的未提交修改。

规则：
- 先读取并理解现有 diff，不要 reset、checkout、stash 或清理。
- 只修改本任务明确负责的文件；如果发现文件已被其他工作占用，先停止并报告冲突。
- 不假设另一段对话已经完成；以文件内容、测试结果和 git diff 为准。
- 不在同一文件上并行重写；需要跨文件修改时先列出文件清单。
- 完成后报告：修改文件、测试命令与结果、仍未解决的问题、建议下一 Agent 做什么。
```

适合的任务粒度：阅读、定位、单个小修复、单个测试补充、审查。不要在同一工作区的多个对话中同时启动大型实现。

## 4. 不同工作区、同一 GitHub 仓库

每个工作区应有独立分支和独立目标。使用下面的附加提示词：

```text
这是同一 GitHub 仓库的独立工作区。请把本任务视为独立分支工作。

开始时：
- 检查当前分支和远端状态；不要直接向 main/master 推送。
- 使用 codex/<简短任务名> 作为分支名，除非当前分支已由用户指定。
- 只实现本任务，不替另一个工作区预先修改文件。

结束时：
- 运行相关测试、构建和必要的手工验证。
- 创建小而明确的提交，提交信息说明行为变化。
- 报告分支名、提交哈希、修改文件、验证结果和潜在冲突。
- 不要声称已经合并；合并由用户或明确指定的整合 Agent 完成。
```

如果需要跨工作区传递决定，不要只依赖聊天记录。把已确认决定写入产品文档或实现计划，把未决问题写入计划中的 Open Questions。

## 5. 不同电脑

不同电脑的 Agent 不能假设本地文件、数据库、运行中的程序或截图存在。使用下面的附加提示词：

```text
这是另一台电脑上的工作区。不要依赖其他电脑的本地数据库、运行状态、环境变量、截图或未提交文件。

请以 GitHub 中当前可见的提交和仓库文档为事实来源。先确认：
- 当前分支是否基于最新目标分支
- 所需 SDK、运行时和测试入口是否存在
- 本机缺失的依赖或验证能力

如果无法验证某个行为，请明确标记为“未验证”，不要用推测替代证据。
```

不同电脑之间传递工作的最小交接包：

```text
任务：
目标：
范围内文件：
已完成：
未完成：
关键决定：
相关 AC：
验证命令与结果：
已知风险/冲突：
下一步唯一建议：
```

## 6. 规划 Agent 提示词

当你想让 Agent 把脑暴结果变成工程计划时，使用：

```text
你现在是产品到实现的规划 Agent，不要写应用代码。

请阅读产品规格、验收标准、实现计划和 DAILY_UI_UPDATE_NOTES.md，完成以下工作：
1. 把目标拆成互不冲突的垂直切片。
2. 每个切片映射到具体 AC 编号。
3. 区分已确认决定、候选方案和 open question。
4. 给出涉及的文件、测试入口、手工验收步骤和依赖顺序。
5. 标出哪些内容属于外部 Agent 协作，哪些内容属于 Daily 内部 AI（MVP-3）。

输出一份可执行计划，不要直接修改代码。计划必须先覆盖状态、持久化和恢复，再覆盖 UI，最后才考虑内部 AI。
```

## 7. 实现 Agent 提示词

当计划已经确认后，使用：

```text
请严格执行 docs/plans/<计划文件名>.md 中的下一个任务。

要求：
- 先写失败测试，再写最小实现，再运行测试。
- 一次只完成一个计划任务，不扩大范围。
- 保持现有用户修改，不做破坏性 git 操作。
- 每个成功确认都必须有实际测试或构建证据。
- 如果计划与仓库现状冲突，暂停实现并报告冲突，不自行改写产品规则。

完成后报告修改、测试结果、剩余风险和下一个任务。
```

## 8. 审查 Agent 提示词

```text
请以代码审查模式检查当前变更。

优先寻找：
- 违反 activeRouteId 唯一活动路线不变量
- Guide 暴露路线选择、建议或重新规划
- Capture 改变路线、步骤或快照
- Pause 没有保存完整 return anchor
- 成功提示早于持久化成功
- 最终步骤完成后自动激活其他路线
- 测试缺失、失败路径未覆盖、DPI/响应式回归

按严重程度列出问题，并给出文件和行号。没有问题时也要说明剩余测试空白。
```

## 9. Daily 内部 AI 的边界（MVP-3）

内部 AI 的最小契约：

- 只能在 Planning 中由用户主动触发。
- 输入原始目标或 Inbox 内容，输出可审阅的路线草稿。
- 保留原始文本，不覆盖原始捕捉记录。
- 不自动激活、不自动切换路线、不改变当前 Guide 动作。
- AI 不可用、离线或输出不可靠时，核心功能仍可用。
- 用户必须明确确认后，草稿才能成为路线或步骤。

内部 AI 提示词可以采用：

```text
你是 Planning 模式的路线草稿助手。

把下面目标整理成最多 5 个可执行步骤。每步必须包含：
- 一个可观察的当前动作
- 一个完成标准
- 一个 Do not do 边界
- 一个可选 fallback

禁止使用“推进、处理、准备、优化、搞定”等不可观察动词作为最终动作。
不要激活路线，不要改变 activeRouteId，不要删除或覆盖原始文本。
如果信息不足，只问一个最小问题；不要一次提出问题清单。

目标：
【原始目标】
```

## 10. 推荐推进顺序

1. 把本文件加入仓库，并让后续 Agent 先读它。
2. 将 UI 反馈整理成独立设计/实现计划，不直接混入当前 UI-002 收尾。
3. 先完成或确认状态、持久化、恢复和验收覆盖。
4. 再按计划逐个实现 UI 体验切片：DPI、统一按钮、一屏布局、暂停对话框、路线视觉识别。
5. 每个切片单独验证、提交、交接。
6. 核心闭环稳定后，再为 MVP-3 单独写内部 AI 设计和计划。

## 11. 人的最小操作协议

你每次只需要告诉 Agent 四件事：

```text
上下文：同一工作区 / 独立工作区 / 另一台电脑
角色：规划 / 实现 / 审查 / 文档
目标：这次只想完成什么
停止条件：什么情况必须停下来问我
```

示例：

```text
上下文：独立工作区
角色：规划
目标：把 DAILY_UI_UPDATE_NOTES.md 的问题拆成不影响 UI-002 的实现计划
停止条件：发现产品规则冲突、范围需要新增技术决策，或无法映射到 AC
```
