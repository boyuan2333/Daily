# E1 影响评估 v1

- 状态：影响评估草案（2026-09-21）。为 D1 已确认的信息架构估算代码与数据改造面；不含排期承诺，不修改产品规则。
- 依据：[D1 信息架构草案](D1-信息架构草案-v1.md)（已评审确认）、[D1 概念地图与术语表](D1-概念地图与术语表-v1.md)、[实施计划](../IMPLEMENTATION_PLAN.md)、当前 `src/` 与 `tests/` 实况。
- 评估范围（D1 §11 指定）：任务投影如何复用步骤身份；日期 / 目标 / 任务流蓝图是否需要新持久化；历史事件是否可用；主窗与挂件同源控制如何实现。保留现有项目与锚点语义。

## 1. 结论摘要

1. **领域层改造便宜，但有构造签名风险。** `Route` / `Step` 是位置参数 `record`（`Models.cs:26`、`Models.cs:43`），新增字段必须做成末尾可选参数并给默认值，否则会连锁改到测试、fixture 与 UI 的所有构造点。
2. **持久化是单行 JSON 文档，不是关系表。** 全部状态存在 `app_state(id=1, payload TEXT)` 一行里（`SqliteStateStore.cs:36-42`、`SqliteStateStore.cs:76-79`）。因此日期、目标、任务流蓝图**都不需要新 SQL 表**，只在文档里加字段/集合；代价是**当前没有 schema 版本与迁移机制**。
3. **Task 不需要新实体。** Task＝Step 的 Planning 投影；日历、任务页、按项目/按目标分组都是同一 `Route.Steps` 集合的查询投影（`RouteListPresentation.cs:41-57` 是现成先例）。
4. **真正缺的数据有三处：** ① 步骤的计划日期；② 项目实体（`Route` 至今没有 project 字段，`MainWindow.xaml:171` 的「按项目」按钮因此被禁用）；③ 历史事件（Review 的前置；现在只保留暂停/切换快照，不记录开始与完成事件）。
5. **任务流是唯一新增聚合。** 需要蓝图实体 + `Route` 上的实例引用（`SourceTaskFlowId`）；「蓝图编辑不回写旧实例」必须由不可变记录在领域层保证。
6. **UI 最大改造是导航与工作区。** `PlanningDestination` 目前只有 `Routes / Inbox / Archive`（`CapturePresentation.cs:5-10`），要扩成 4 主板块 + 归档次级，牵动 `MainWindow.xaml` 的导航栏与三套工作区、`RenderPlanning`（`MainWindow.xaml.cs:136`）、响应式 list-to-detail（`ResponsivePlanningPresentation.cs`）以及 `CaptureContext` 的上下文锁定。
7. **专注模式/桌面挂件是独立窗口 + 共享同一执行状态**，是本评估最大且最独立的一块；D1 已声明它是 v2 候选，现有 MVP-2 只承诺托盘/快捷键/可选启动。
8. **现有 62 个测试不会被新增字段破坏**，前提是新字段可选、新集合默认空；但 D1 的新行为（任务页、日历、任务流、回顾、挂件）目前**零覆盖**，需要补领域/持久化/原型三层证据。

## 4. 数据与持久化影响

### 4.1 新增字段/集合清单

| 对象 | 新增 | 类型 | 默认/兼容 |
| --- | --- | --- | --- |
| `Step` | `PlannedDate` | `DateOnly?` | null＝无日期，不补假日期 |
| `Step` | `PlannedTime`（若采用） | `TimeOnly?` | null＝当日全天行 |
| `Route` | `ProjectId` | `Guid?` | null＝未分配 |
| `Route` | `GoalText` | `string?` | null＝无目标 |
| `Route` | `SourceTaskFlowId` | `Guid?` | null＝非任务流实例 |
| `AppState` | `Projects` | `IReadOnlyList<Project>` | 缺省＝空 |
| `AppState` | `TaskFlows` | `IReadOnlyList<TaskFlow>` | 缺省＝空 |
| `AppState` | `History` | `IReadOnlyList<HistoryEvent>` | 缺省＝空 |

### 4.2 向后兼容

- `StateDocument`（`SqliteStateStore.cs:85-97`）用位置参数 record 反序列化；旧 payload 缺少的新属性会取 `default(T)`，**引用类型会得到 `null`**。因此新集合必须在 `StateDocument.ToState()` 里归一到空数组，不能直接透传。
- `Route` / `Step` 新增参数必须放在末尾且带默认值，避免改动既有构造点（`Models.cs:35-41`、`Models.cs:49-54`，以及测试与 `UiFixture/Program.cs:91-113`）。
- **建议新增 `SchemaVersion` 字段**，为后续真正的迁移留出口；本卡只提出建议，不擅自改动。

### 4.3 迁移与删除

- D1 要求「旧记录不补假日期」「归档可逆」「不得隐式删除」。新增字段全部可空即可满足，**不需要回填脚本**。
- 任务流蓝图编辑不回写实例：领域层用不可变记录 + 新 Route 实例承载，天然满足。

## 5. 历史事件缺口（Review 的前置）

- 现状：只有 `ExecutionSnapshot`（暂停/切换时写入，`Models.cs:425-447`、`Models.cs:355-372`）。**步骤完成、路线开始、路线完成都没有事件记录**——完成只体现为 `Step.IsCompleted = true`（`Models.cs:492-494`）。
- 因此 Review 的时间线没有可用数据源，D1 §6 也明确禁止从锚点推算时长或伪造次数。
- 影响：Review 不能只做 UI，必须先补一个只增不改的 `HistoryEvent` 集合，并在 `CompleteCurrentStep` / `SelectActiveRoute` / `Pause` 等既有转换点追加写入。
- 规模：M（领域 + 持久化 + 测试），独立于 UI，可以早做。

## 6. UI 影响

- **导航**：`MainWindow.xaml:134-136`（导航栏）与 `:149-152`、`:228-231`、`:264-267`（三处窄屏导航）都是硬编码按钮，扩成 4 主板块 + 归档次级要同时改这几处，并复用现有选中态逻辑（`SetSelected`，`MainWindow.xaml.cs:1235`）。
- **`PlanningDestination` 扩展**：新增 TaskBoard / RoutesAndFlows / Review，并把 `Archive` 降为次级；`CaptureContext.PlanningDestination`（`CapturePresentation.cs:12-22`）随之外扩，保证捕获的上下文锁定仍成立。
- **响应式**：`ResponsivePlanningPresentation` 目前只允许 Routes/Inbox 开详情（`:40-42`），新目的地需要各自的 list-to-detail 与上下文（滚动、选中、分组、展开）恢复。
- **任务页 / 日历 / 回顾 / 任务流**：四套新工作区。建议把投影逻辑放进独立纯函数呈现类（照 `RouteListPresentation` 风格），让查询逻辑可单测，XAML 只负责渲染。
- **挂件**：需要新窗口 + 显隐控制；同一 `ExecutionSession`，不得引入第二状态机。紧凑尺寸下仍要能读到完成标准（D1 §8、IA-04）。

## 7. 测试与验收影响

- 现有 62 个测试（App 35 / Domain 22 / Persistence 5）覆盖领域不变量、会话失败写入、呈现投影与少量 XAML 断言；**新增字段不会破坏它们**。
- D1 的 V-01 至 V-12（`D1-信息架构草案-v1.md:326-341`）目前**没有对应覆盖**，需要新增：
  - 领域/持久化：日期分桶、项目归属隔离、蓝图/实例隔离、历史事件只增、重启恢复不变。
  - 呈现：任务投影、日历分组、按项目/目标分组、回顾只读。
  - UI/手工：`MANUAL_ACCEPTANCE.md` 需扩充新板块流程；窄屏往返与位置恢复。
- 验收对照需要扩充 `ACCEPTANCE.md`（D1 明确「新项批准后再扩充覆盖」）。
- 现有 `UiFixture`（`tests/ExecutionContinuity.UiFixture/Program.cs`）是现成的隔离数据注入器，新增字段后应扩充 fixture 以支持新板块的人工验收。

## 9. 风险与未决

1. **无 schema 版本**：JSON 文档存储目前没有版本号；若将来字段语义变化，无法区分旧新 payload。建议尽早加 `SchemaVersion`。
2. **`MainWindow.xaml.cs` 已是 51KB 单体**：继续往里堆四套工作区会显著提高维护成本。建议新板块尽量抽成独立 UserControl 或独立呈现类，但这属于重构，需要单独评估。
3. **`PlanningDestination` 定义在 `CapturePresentation.cs`**：位置与职责不符，扩展时建议顺手移到更合适的位置（小重构，需同步测试）。
4. **挂件同源控制**：WinUI 3 非打包应用下第二窗口与主窗共享同一 `ExecutionSession` 的可行性需要在 D-2 原型验证；D1 要求「不引入第二状态机」。
5. **任务页跨路线列举的性能**：当前状态全量在内存，本地单用户规模下不成问题；但需确认大规模步骤数下日历/任务页查询不会阻塞执行写入（D1 §11 已提出该约束）。
6. **UI-002 归档恢复仍在侧分支**：Archive 降为次级入口后，UI-002 的改动需要与导航重构合并，存在冲突风险。

## 10. 明确不做

- 不新增 SQL 关系表，不引入 ORM 或迁移框架（除非另开决策）。
- 不实现 D1 之外的板块（不做自动规划、不做统计仪表盘、不做 AI 自动写入）。
- 不在本卡修改产品规则或上游规范文件。
- 不给旧记录回填日期、项目或历史事件。
