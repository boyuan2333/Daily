# P-1：提示资产审计备忘

> 审计日期：2026-09-16（Asia/Shanghai）
>
> 审计范围：根目录 `AGENTS.md`、`docs/` 中面向 Agent 的协作说明、当前产品规格与实现计划。
>
> 处理方式：根 `AGENTS.md` 受保护，无法由本任务直接写入；完整替代内容写入 `docs/plans/P1-AGENTS-proposed.md`，由操作员评审后应用。

## 1. 审计结论

当前产品规则本身不需要重写。需要调整的是提示资产的“入口层”：保留稳定的不变量，把文档引用改成按任务场景路由，把已经确认的技术决策与历史阶段说明分开，并给执行型任务明确的完成标准和安全本地操作权限。

OpenAI 的 GPT-6 Astra 指南给出的直接依据是：根文档应尽量短，并通过场景化指针实现渐进披露；“每次编辑前阅读整套文档”会浪费上下文；过去用于督促旧模型反复测试或逐步请示的文字，可能让 Astra 在首轮实现后过早停下或变得过于保守。[1]

## 2. 根 `AGENTS.md` 提案

完整提案见 `docs/plans/P1-AGENTS-proposed.md`。提案保留了现行 `Product Boundary`、`Non-Negotiable Behavior` 和 `Scope Guardrails` 的全部产品规则；没有新增产品行为，也没有删除任何产品约束。

提案的结构变化如下：

| 改动 | 处理方式 | 理由 |
| --- | --- | --- |
| 保留产品边界 | 原样保留产品定位、Guide / Planning 规则、单一 `activeRouteId` 不变量、Capture / Pause / Stuck / Completion 规则及 MVP 范围 | 这些是产品事实，不应因模型升级而弱化 |
| 收敛工程守则 | 保留状态建模、原子持久化、技术决策记录和验收映射；删除“文档阶段禁止写应用代码”的全局限制 | 当前仓库已经进入 WinUI / SQLite 实现阶段；限制应绑定任务类型，而不是继续覆盖整个仓库 |
| 增加 `Context by Task` | 按产品状态、UI、技术选型、Windows 验收、历史背景分别指向 `docs/` 文件 | 对应原文的场景化引用与渐进披露建议，避免每次修改都读取整套文档。[1] |
| 增加 `Completion & Permissions` | 允许在任务范围内自动执行本地编辑、构建、测试和失败重跑；要求记录实际证据；要求继续到验证和修复完成 | 给 Astra 足够的安全边界和推进权限，同时保留真实人类决策的边界。[1] |
| 保留人类决策边界 | 只有真正需要产品或外部访问决策时才一句话说明所需决策；不授权修改真实用户数据或绕过工具安全门 | “减少请示”不等于取消数据安全和授权边界 |

## 3. `docs/` 协作说明审计清单

以下是“过度指引 / 过时点 → 建议清单”。本卡只记录建议，不逐一修改这些文件。

### 3.1 `docs/UI_FIX_BACKLOG.md`

- 过度指引：第 9—23 行要求新 Session 先阅读固定文件栈、按模型等级自行认领、先回填认领信息，并要求并发时人工分配。建议把它收敛为短入口：任务由 kanban 卡分配；worker 只读取本任务需要的来源；并发协调由 kanban 负责，不由仓库文档模拟。
- 过度指引：第 25—33 行的 A / B / C 模型等级和“等级不足不要认领”属于旧式模型路由。建议保留风险标签作为任务元数据，但不要让 worker 自行根据模型等级做任务分配。
- 重复指引：第 50 行再次强调必须有实际验证，第 360—371 行又要求手工回填。建议保留一个简短的结果模板，把具体验收标准放回任务卡或对应计划。
- 状态风险：第 54—56 行仍记录 51 个测试的旧基线，而第 289—294 行已经记录 UI-006 的 62/62 结果；第 261 行仍把 UI-006 标为“进行中”，但第 289 行已写“已完成”。建议下一次 backlog 维护时刷新基线和状态，或明确标记“历史快照”。
- 事实边界：UI-005 的项目字段阻塞和 UI-006 的项目搜索阻塞记录是有价值的，应保留；它们应被视为当前模型缺口，而不是让 worker 通过假数据完成任务。

### 3.2 `docs/IMPLEMENTATION_PLAN.md`

- 过时 / 矛盾：第 9 行仍写 `Tech Stack: To be confirmed`，但第 44—47 行已经确认 SQLite、`Microsoft.Data.Sqlite.Core`、WinUI 3 和 .NET 10。建议改成“已确认技术栈”，候选项只留在 Open Technical Questions。
- 过时 / 矛盾：第 72 行仍写“先解决 SQLite-versus-JSON question”，但 SQLite 已经是确认决策。建议改成直接实现已确认的 SQLite 持久化边界。
- 范围表达：第 74 行“Do not build a desktop UI...”对 MVP-0 有效，但容易被理解为当前仓库全局禁令。建议改为“During MVP-0, do not...”并在 MVP-1 开始处明确解除范围。
- 正向保留：第 96—125 行的 Acceptance-to-Test Mapping 是高价值路由，应作为任务按场景引用的主索引，不要求每个 worker 全文阅读。

### 3.3 `docs/plans/*.md`

- 过度指引：`2026-08-01-stitch-ui-sync.md`、`2026-08-05-ui-004-responsive-navigation.md` 和 `2026-09-04-ui005-route-list.md` 的 `For Codex / For Claude` 与 `REQUIRED SUB-SKILL` 是模型或外部工作流绑定。建议新计划只说明目标、文件边界、验收证据和必要来源，把具体调度交给 kanban / 当前 Agent 环境。
- 过度指引：这些计划大量采用“Step 1 / Step 2 / Step 3”的逐动作配方。建议保留可验收的阶段和测试意图，但不规定强制的每一步操作顺序；Astra 指南明确提醒，过度具体的 itinerary 可能阻碍强模型处理真实上下文。[1]
- 过时表达：UI-005 和 UI-006 的计划仍保留实现前的候选 / 占位叙述，但 backlog 已有实际结果。建议将已完成计划标为历史实施记录，新增任务使用短 brief 指向它们。
- 正向保留：UI-006 对 raw capture 不可变、organized text 可编辑、SQLite commit 边界的描述属于清晰的行为约束，不应因精简而丢失。

### 3.4 `docs/TECHNICAL_SPIKE.md`

- 明确过时：第 11、44、58 行仍记录“没有 .NET SDK”“等待授权安装 .NET 10 SDK”。仓库当前已有 WinUI 应用代码与实现计划中的确认技术决策。建议保留该文件作为带日期的历史环境快照，并在顶部加“Historical snapshot — recheck before use”；不要让新任务把它当作当前环境事实。
- 范围风险：第 60—68 行把 Spike 的成功条件写成后续整体路线，包含 tray / shortcut；建议在重新使用前拆出“Spike 历史成功条件”和“当前 MVP 验收”，避免把条件性探索误当成已确认产品要求。

### 3.5 `docs/MANUAL_ACCEPTANCE.md`

### 3.6 `docs/DAILY_UI_UPDATE_NOTES.md`

- 可读性问题：当前文件读取结果显示内容几乎全部挤在首行，标题和段落边界不可稳定识别。建议另立文档整理任务恢复 Markdown 分段，并把“原始反馈 / 已确认决策 / 待实现计划”显式分开。
- 事实边界：其中视觉候选和方案 A / B 是设计输入，不应被 Agent 当作已批准产品规则；现有文件已写明这一点，后续整理时应保留。

## 5. 未来 kanban 卡 worker 简报要点

未来卡片应控制在短 brief，并包含以下 5 项：

- 明确交付物路径、任务范围和不做事项；产品规则通过 `AGENTS.md`、对应规格和验收条目按场景引用，不复制整套背景。
- 先写完成标准：需要实现什么、需要观察什么、哪些证据足以关闭卡片；不要只写“完成实现”。
- 明确安全的本地权限：可在任务范围内读写代码、运行隔离 fixture 的 build / test、检查结果并修复由本次改动造成的失败，无需逐步请示。
- 要求“跑通 + 检查结果 + 修复失败 + 重跑”后才算完成；不要在第一版实现后自动停下等待评审，除非卡片明确设置该检查点。[1]
- 结束时回填实际命令、结果、未验证项和残留风险，并调用 `kanban_complete` 或 `kanban_block`；不要只留下过程评论。
